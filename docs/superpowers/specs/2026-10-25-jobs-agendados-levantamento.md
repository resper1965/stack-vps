## Observações transversais

- **CodeQL (itens 3, 7, 9, 10 e o job `codeql-analysis` do 8).** Em repositório privado exige licença GitHub Advanced Security. As Actions `codeql-action/*` e `upload-sarif` gravam no painel Code scanning do GitHub, que não existe fora dele. Substituto: Semgrep (SAST) + gitleaks (segredos) + osv-scanner (dependências). Perde-se a análise de fluxo de dados do CodeQL; o Semgrep OSS cobre bem padrões, menos taint entre arquivos.
- **Onde gravar o resultado fora do GitHub.** Hoje os jobs gravam em SARIF/Code scanning, artefato com retenção de 30 dias ou issue. Proposta: um diretório `/var/lib/jobs/<repo>/<data>/` com JSON/SARIF e um resumo de uma linha enviado ao canal de alerta escolhido (ver decisões).
- **Checkout.** Fora do GitHub, todo job precisa clonar o repositório (deploy key ou token só de leitura). Vale para os 10.
- **Fuso.** Os crons ficam em UTC; um timer systemd com `OnCalendar=` em UTC (ou `TZ=UTC` no crontab) preserva os horários.
- **Atribuição de IA (observação).** O workflow `vigilancia` (n.360-alternative) tem, no corpo da issue que abre, a linha `_Generated by [Claude Code](https://claude.ai/code)_`. Ao migrar para script, não levar essa linha.

## Fichas

### 1. DocVault, Nightly E2E (`.github/workflows/nightly.yml`)

- **O que faz.** (1) checkout; (2) Node 22 com cache npm; (3) `npm ci`; (4) `npx playwright install chromium --with-deps`; (5) `npx playwright test` contra produção; (6) sobe `playwright-report/` como artefato (30 dias), sempre; (7) em falha, só imprime `::error::` (não notifica ninguém).
- **Cron.** `0 5 * * *`, UTC. Também `workflow_dispatch`. Timeout de 30 min.
- **Para rodar fora.** Node 22, npm, Chromium do Playwright com dependências de sistema (melhor a imagem `mcr.microsoft.com/playwright`). Alvos: `https://app.docvault.esper.ws`, `https://admin.docvault.esper.ws`, `https://docvault.esper.ws` (produção, pela internet). O reporter é definido em `playwright.config.ts` (`github` + `html` em CI); não li esse arquivo.
- **Segredos.** `E2E_EMAIL`, `E2E_PASSWORD` (conta de teste em produção). Variáveis: nenhuma; as URLs estão no arquivo.
- **Grava.** Só o artefato HTML (30 dias). Nada em DefectDojo, SARIF ou issue.
- **Recursos.** Até 30 min (teto); Chromium pede cerca de 1 a 2 GB de RAM. Tráfego real contra produção toda noite.
- **Dependência de recursos do GitHub.** `upload-artifact` e cache do `setup-node`: substituíveis por pasta local. Nada de Code scanning.
- **Recomendação.** Container Playwright rodando `npx playwright test` por timer na VPS, relatório em pasta datada com retenção de 30 dias, e aviso real em falha (o original só escrevia no log). Risco baixo; atenção à conta de teste em produção e à RAM da VPS.
- **Classificação.** Médio.

### 2. aegis-itms, Nightly Security & DefectDojo (`security-nightly.yml`)

- **O que faz.** (1) checkout; (2) pnpm 8; (3) `pnpm audit --json > pnpm-audit.json` (ignora falha); (4) Semgrep com `p/default` e SARIF (continue-on-error); (5) Trivy `fs` em JSON; (6) envia o relatório do **Trivy** ao DefectDojo (`/api/v2/import-scan/`, `scan_type=Trivy Scan`, engagement `<nome>-NIGHTLY`, ambiente Development), sempre. O `pnpm-audit.json` e o SARIF do Semgrep não são enviados nem guardados: só o Trivy sai do runner.
- **Cron.** `0 2 * * *`, UTC. Também manual.
- **Para rodar fora.** Node + pnpm 8, Semgrep, Trivy, curl. O Semgrep `p/default` baixa as regras do registry (precisa de internet). Serviço externo: instância do DefectDojo em `DEFECTDOJO_URL`.
- **Segredos.** `DEFECTDOJO_URL`, `DEFECTDOJO_API_TOKEN`, `DEFECTDOJO_PRODUCT_NAME`, `DEFECTDOJO_ENGAGEMENT_NAME`. Variáveis: nenhuma.
- **Grava.** DefectDojo (só Trivy). Nada mais é persistido.
- **Recursos.** Poucos minutos; o Trivy baixa o banco de vulnerabilidades (cache local resolve).
- **Dependência de recursos do GitHub.** Nenhuma real (sem Code scanning). `trivy-action@master` e `semgrep-action@v1` são só empacotamento.
- **Recomendação.** Script `semgrep` + `trivy fs` + `pnpm audit`, com `curl` ao DefectDojo se ele ainda existir. Risco: o DefectDojo pode já não existir; sem ele o job precisa de outro destino.
- **Classificação.** Depende de decisão do dono (D3).

### 3. be-secure, CodeQL — Security Scan (`codeql.yml`)

- **O que faz.** CodeQL para `javascript-typescript`: init, autobuild, analyze. Roda também em push/PR para `main`.
- **Cron.** `0 6 * * 1`, UTC (segunda).
- **Para rodar fora.** Nada sem o GitHub: o resultado vai para o Code scanning.
- **Segredos / variáveis.** Nenhum (usa o `GITHUB_TOKEN` implícito com `security-events: write`).
- **Grava.** Painel Code scanning do GitHub.
- **Recursos.** Minutos; o CodeQL consome RAM em projetos grandes.
- **Dependência de recursos do GitHub.** Total: `codeql-action` e Code scanning; em repositório privado exige GHAS.
- **Recomendação.** Semgrep (`p/javascript`, `p/typescript`, `p/owasp-top-ten`) + gitleaks + osv-scanner no lockfile, semanal. Risco: taint menos profundo que o do CodeQL; sem painel de triagem; o gatilho em push/PR só sobrevive se a CI ficar no GitHub.
- **Classificação.** Depende de decisão do dono (D1, D2).

### 4. dns-repair, Verificação diária de DNS (`dnscheck.yml`)

- **O que faz.** (1) checkout; (2) Python 3.12; (3) `python3 dnscheck.py --all` compara as zonas vivas na Cloudflare com `zones/*/spec.py` e guarda saída e código de saída; (4) se divergir, abre issue `DNS divergente — <data>` com rótulo `dns-drift` (ou comenta na issue aberta, para não abrir uma por dia); (5) se existir `HOSTINGER_API`, roda `python3 wpaudit.py` (auditoria das instalações WordPress); (6) falha o job se houve divergência de DNS ou se `wpaudit` retornou 1.
- **Cron.** `0 10 * * *`, UTC (o arquivo comenta que é 07:00 em São Paulo). Também manual.
- **Para rodar fora.** Python 3.12 e o próprio repositório (`dnscheck.py`, `wpaudit.py`, `zones/`). Serviços: API da Cloudflare e API da Hostinger. Não li os scripts; o workflow não faz `pip install`, então presumivelmente só usam a biblioteca padrão.
- **Segredos.** `CLOUDFLARE_API_TOKEN`, `HOSTINGER_API` (opcional). Variáveis: nenhuma.
- **Grava.** Issues do GitHub (rótulo `dns-drift`) e o log do job.
- **Recursos.** Segundos; só chamadas de API.
- **Dependência de recursos do GitHub.** `actions/github-script` para abrir issue. A comparação é Python puro.
- **Recomendação.** Timer na VPS com `python3 dnscheck.py --all; python3 wpaudit.py`, saída em arquivo e aviso só quando o código de saída for diferente de 0. A deduplicação (uma notificação por divergência) pode ser um arquivo de estado com o hash da saída. Se quiser manter a issue, `gh issue create` basta (um token com escopo de issues). Risco baixo; o token da Cloudflare deve ser somente leitura de DNS.
- **Classificação.** Trivial.

### 5. n.360-alternative, vigilancia (`vigilancia.yml`)

- **O que faz.** Dois jobs paralelos. **auditoria:** checkout, Node 22 + `npm ci`, `npm audit --omit=dev --json`, soma de low/moderate/high/critical; se o total não for zero, abre issue (rótulo `seguranca`, com fallback sem rótulo). **deriva:** Postgres 17 como serviço (porta 55432, `trust`), `npm ci`, `npm run typecheck`, `npm test` contra a `main`, para pegar dependência transitiva que mudou sem o código mudar.
- **Cron.** `0 6 * * 1`, UTC (segunda). Também manual.
- **Para rodar fora.** Node 22, npm, Postgres 17 em container (`POSTGRES_HOST_AUTH_METHOD=trust`, porta 55432; `DATABASE_URL=postgres://postgres@127.0.0.1:55432/postgres`), `gh` ou outro canal para o alerta.
- **Segredos.** Nenhum além do `GITHUB_TOKEN` implícito (abrir issue). Variáveis: nenhuma.
- **Grava.** Issues do GitHub. Falha do job `deriva` fica só no status do workflow.
- **Recursos.** Poucos minutos; um Postgres leve.
- **Dependência de recursos do GitHub.** Service container (substituível por `docker run`) e `gh issue create`. Nada de Code scanning.
- **Recomendação.** Script com `docker run postgres:17`, `npm ci`, `npm audit`, `typecheck`, `test`; sair com código diferente de 0 e avisar. O próprio texto do workflow diz que falha silenciosa de job agendado equivale a não rodar, então o canal de alerta faz parte da entrega. Risco baixo a médio, justamente por isso.
- **Classificação.** Médio.

### 6. n.360-alternative, backup (`backup.yml`)

- **O que faz.** Job `dump`: instala o cliente PostgreSQL 17 (PGDG); abre sessão `psql` com `pg_export_snapshot()` em `REPEATABLE READ READ ONLY`, para que tudo saia de um só snapshot; `pg_dump -Fc` do schema `public` completo, da estrutura de `auth` e dos dados de `auth.users`, `auth.identities`, `auth.mfa_factors`; gera `manifesto.txt` (contagens, última migration, digest e elos quebrados da cadeia `trilha`, sem dado pessoal); empacota e **criptografa** (`openssl enc -aes-256-cbc -pbkdf2 -iter 600000`, passphrase de segredo); registra o sha256 do `.enc`; sobe `backup.tar.enc` + manifesto como artefato (30 dias). Job `restaurar`: Postgres 17 efêmero, baixa o artefato, confere o sha256, descriptografa, cria os papéis `anon`/`authenticated`/`service_role`, restaura `auth` (estrutura, dados) e `public`, e compara cada contagem e o digest da trilha com o manifesto; qualquer divergência deixa o workflow vermelho.
- **Cron.** `17 6 * * *`, UTC. Também manual, com escolha de ambiente (`desenvolvimento` ou `producao`; o agendado usa `producao`). Concorrência serializada, nunca cancela. Timeout de 30 min por job.
- **Para rodar fora.** Bash 4+ (usa `coproc`), `pg_dump`/`psql`/`pg_restore` na versão 17 ou maior (o servidor é 17), `openssl`, `tar`, `sha256sum`, Docker (ou um Postgres 17) para a restauração de teste. Serviço externo: banco Supabase de produção. A conexão tem de ser direta ou de sessão, não pooler em modo transação (senão o snapshot não exporta). `PGSSLMODE=require`.
- **Segredos.** `DATABASE_URL`, `BACKUP_PASSPHRASE`, ambos por **environment** (`producao`/`desenvolvimento`). Variáveis: nenhuma.
- **Grava.** Artefato do GitHub por 30 dias, sem outro destino: é o único lugar onde a cópia fica. O runbook citado no cabeçalho (`docs/runbooks/backup-e-restauracao.md`) não foi lido.
- **Recursos.** Dump + restauração, teto de 2 x 30 min; tamanho do banco desconhecido (Supabase gratuito, no máximo 500 MB); precisa de disco para o dump em claro e o cifrado ao mesmo tempo.
- **Dependência de recursos do GitHub.** Artefato (retenção) e service container. A lógica é shell e é portável quase sem alteração. O ponto fraco é o destino: fora do GitHub é preciso um lugar para o arquivo cifrado.
- **Recomendação.** Reaproveitar o script quase como está (extrair os blocos `run:` para `backup.sh` e `restaura.sh`), trocar `upload-artifact` por cópia para armazenamento fora da VPS e manter retenção de 30 dias com limpeza. A restauração de teste deve continuar em toda execução; sem ela perde-se a garantia que motivou o job. Risco médio: é a única cópia do banco (sem backup nativo nem PITR no plano gratuito) e a passphrase passa a viver fora do cofre de segredos do GitHub.
- **Classificação.** Médio (a mecânica é quase trivial; a decisão é onde guardar e como proteger a passphrase, ver D5).

### 8. n.discovery, Security (`security.yml`)

- **O que faz.** Seis jobs independentes. **codeql-analysis:** idêntico ao item 7 (duplicado). **secret-scanning:** gitleaks com histórico completo e `.github/gitleaks.toml`. **dependency-review:** só em PR; falha em severidade moderada ou maior e nega licenças GPL-2.0/GPL-3.0. **owasp-dependency-check:** Python 3.11, `pip install -r requirements*.txt`, OWASP Dependency-Check sobre `./src` e os requirements, falha com CVSS 7 ou mais, relatório em `reports/` (30 dias). **owasp-bandit:** `bandit -r src/` em JSON e texto, relatório como artefato e, em PR, comentário via `tj-actions/bandit`. **trivy-scan:** Trivy `fs` em SARIF (CRITICAL,HIGH, `exit-code: 1`), enviado ao Code scanning por `upload-sarif`.
- **Cron.** `0 2 * * *`, UTC (também push/PR em `main` e `develop`).
- **Para rodar fora.** Python 3.11 + pip, gitleaks, bandit, Trivy e OWASP Dependency-Check (precisa de Java e baixa a base NVD, pesada e lenta sem chave de API da NVD). Serviços externos: bancos de vulnerabilidades (NVD, Trivy DB).
- **Segredos.** `GITHUB_TOKEN` (usado pelo gitleaks-action; fora do GitHub é desnecessário). Variáveis: nenhuma.
- **Grava.** Artefatos (OWASP e bandit, 30 dias), Code scanning (Trivy) e comentário em PR. Fora do GitHub, vira pasta local.
- **Recursos.** O mais pesado do conjunto: o OWASP Dependency-Check leva vários minutos e baixa centenas de MB na primeira vez; o histórico completo do gitleaks cresce com o repositório.
- **Dependência de recursos do GitHub.** `upload-sarif` (Code scanning, sem equivalente), `dependency-review-action` (grafo de dependências do GitHub, só em PR) e comentário em PR. O resto é portável.
- **Recomendação.** Rodar gitleaks, bandit, Trivy fs e osv-scanner (no lugar do OWASP Dependency-Check, muito mais leve, mantendo o corte por severidade) em script diário; descartar o `dependency-review` e o CodeQL duplicado. A regra de licença GPL pode virar `pip-licenses`, se o dono ainda a quiser. Risco baixo; trocar OWASP DC por osv-scanner muda a base de dados e pode mudar os achados.
- **Classificação.** Médio.

## Decisões que dependem do dono

- **D1. Visibilidade dos repositórios.** O CodeQL só roda de graça em repositório público (ou com licença GHAS). Confirmar a visibilidade de be-secure, n.discovery, nTransfer e site-sabrina; se algum for público, o workflow pode ser religado no GitHub, sem substituto local.
- **D2. Trocar CodeQL por Semgrep + gitleaks + osv-scanner**, com cobertura menor de taint e sem painel Code scanning, ou pagar GHAS. Decidir também se a varredura passa a rodar só na agenda, sem o gatilho de push/PR que o CodeQL tinha.
- **D3. DefectDojo (aegis-itms).** A instância ainda existe e é para continuar? Se não, o job se reduz a relatório local; se sim, falta definir como a VPS a alcança.
- **D4. Canal de alerta no lugar das issues** (itens 4 e 5 abriam issue; o item 1 só escrevia no log). Sem GitHub é preciso escolher o destino (e-mail, mensagem, arquivo + painel). Sem canal, os jobs viram falha silenciosa.
- **D5. Backup do n.360-alternative.** Onde guardar o `backup.tar.enc` fora da VPS (o restic/R2 foi adiado para a fase 4, mas aqui é a única cópia do banco) e onde fica a `BACKUP_PASSPHRASE` fora do GitHub. Enquanto isso não for decidido, o banco de produção está sem backup.
- **D6. Onde rodam os jobs e como clonam os repositórios** (VPS como estação de trabalho; deploy key ou token somente leitura por repositório), e se o Playwright do DocVault pode usar a RAM da VPS à noite contra produção.
- **D7. Quais jobs religar de verdade.** Vários cobrem o mesmo terreno (n.discovery tem CodeQL duplicado; be-secure e site-sabrina são pequenos). Pode ser aceitável não substituir alguns.
